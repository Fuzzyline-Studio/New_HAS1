## 게임·위치·배터리 현장 검증 전 설정

아래 설정과 통합 게임 검증은 후속 항목이다. 총 8대 초기 설치와 G1P1~G1P8의 OTA·Telnet 실측 완료 범위는 [설치 계획](ROLLOUT.md)에서 별도로 관리한다.

1. TTGO 실물 배터리 종류/셀 수, ADC 배선, 실제 분압비와 보정 범위를 `library_and_pin.h`에 반영한다. 기본값은 측정 보고 비활성이다.
2. 실제 광고명이 `HAS3:장치ID`인지 확인한다. Beetle `beacon_map.h`는 대문자 첫 글자 `B/L/T/S/U/H`를 각 방에 매핑하며, ID는 2~18자의 영문·숫자·`_`·`-`만 허용한다. `BI1/BI2/BR1/BR2/BD1/BD2/BE/BT`가 `bamboo`, `LA`가 `living`으로 보고되는지 확인하고 나머지 네 방도 현장 장치로 검증한다.
3. 리셋선(v24부터 GPIO33, v23까지 GPIO12) 부팅 LOW 유지, Beetle GPIO1 pull-down, 공통 GND, UART 교차 연결, 모터 드라이버(v24부터 PWM이므로 모터 플라이백 다이오드 포함)를 대조한다. 회로도 심벌의 물리 핀 4가 GPIO1이며, 기존 GPIO3 가정은 아래 실기 기록에서 정정했다.
4. 서버 MAC 등록과 G1/G2 장치명, `tagger_name`, 역할/시간/봉헌/개방 필드를 확인한다. 두 보드 첫 USB 설치는 빌드와 같은 min_spiffs 파티션을 사용한다.

## 2026-09-17 버전 지정 OTA·롤백 추가 검증

기존 수동 배포·정수 버전·고정 태그를 유지하고 두 글러브 대상에만 비덮어쓰기 버전 보관 릴리즈를 추가했다. `github@12:7`은 TTGO 12·Beetle 7, `github@12`는 두 보드 모두 12를 뜻한다. 명령과 실제 산출물 형식은 [BUILD.md](BUILD.md)를 따른다.

- 실제 펌웨어의 C++ 호스트 테스트 실행 파일 **9개 통과**. 추가 항목은 엄격한 버전/메타데이터 파서, 실행 중 목표 고정·다음 명령 보관, Beetle NVS 목표 버전/파티션/새 부팅 복구다. 기존 peer 테스트에는 이전 버전 롤백·동일 버전 skip·틀린 목표·완료 후 버전 변경/연결 만료를 포함했다.
- Python 테스트 **14개 통과**. 메타데이터 HMAC, 잘못된 이미지/파티션 서명, 버전/보드 범위, 기존 보관 파일 충돌 시 쓰기 없음, 같은 내용 재시도, 중단된 draft 재개, 소스와 커밋 일치, 다른 호스트로 토큰 전달 방지를 확인했다. GitHub 쓰기는 모의 API로 검증했으며 실제 게시하지 않았다.
- 독립 검토에서 단계 사이 게임/탐색 전환 또는 서버 단절 시 OTA 대기가 게임 처리를 계속 막는 문제를 수정했다. Beetle 완료 후 부적합 페이즈에서는 남은 TTGO 단계를 취소하고, 서버 대기는 작업 시작부터 5분으로 제한했다. 시작 전 TTGO Wi-Fi 단절은 큐를 비운 뒤 실패 처리한다. 이미 쓰기 중인 플래시는 중간에 취소하지 않는다.
- 작성 담당과 다른 검토자가 최종 TTGO/Beetle 상태 처리, 서명 메타데이터와 이미지 검증, 보관 릴리즈 정책 및 문서를 재검토했다. 최종 검토 범위의 미해결 발견 사항은 없다.

## 2026-09-17 최초 USB 설치와 TTGO 복구

- G1P1 테스트 글러브의 TTGO와 Beetle에 실제 배포 키로 빌드한 펌웨어 1 / 파티션 1을 설치했다. 당시 Beetle 리셋 입력은 GPIO3으로 빌드했다. 키는 기존 Release의 이미지·서명과 대조했으며 저장소나 로그에 값을 기록하지 않았다.
- 두 보드 모두 460800 업로드와 네 영역 해시 검증을 통과했다. 변경 영역은 먼저 백업했고, NVS를 포함한 전체 플래시 지우기는 하지 않았다.
- TTGO는 Origin 모드 부팅 및 Wi-Fi 연결, Beetle은 `firmware=1` 부팅을 확인했다. 각각 20초 관찰에서 반복 애플리케이션 부팅·panic·brownout은 관찰되지 않았다.
- 사용자가 이후 TTGO에 다른 펌웨어가 올라갔다고 확인하여 검증된 글러브 이미지를 다시 기록했다. 이 복구에서는 이전 업로드 캐시를 사용하지 않도록 `upload.extra_flags=--no-fast-flash`를 지정했고, 네 영역 해시·Origin 부팅·Wi-Fi 연결을 새로 확인했다.

- 서버 응답 무효와 15초 freshness 만료가 사용하는 두 재동기화 경로에서 Player 초록 4칸, Ghost 파랑 2칸, Tagger 보라 4칸의 RGB·점등 수가 바뀌지 않는 회귀를 추가했다. 안전을 위한 게임 쓰기 차단과 진동 취소는 유지한다.
- `device_state=photo`는 원래 `game_state`와 무관하게 별도 안전 페이즈로 해석한다. Player·Ghost·Neutral은 초록 4칸, Tagger는 보라 4칸이며 Photo 중 게임 쓰기·BLE 스캔·OTA 제한을 유지한다.
- `device_state=exploration` 별칭은 제거했다. 잔존 서버 값이 Active의 일반 상태로 해석되어 게임 쓰기를 재개하지 않도록 해당 snapshot을 무효 처리한다.
- freshness는 14,999ms 유효 / 15,000ms 만료와 `millis()` 순환 경계를 생산 정책 함수로 확인했다.
- C++ 호스트 실행 파일 **15개**, Python 회귀 **16개**가 통과했다. ESP32 core **3.3.11** compile-only에서 TTGO 본게임·훈련·Beetle 세 profile이 모두 성공했으며 프로그램/RAM은 각각 **1,089,737 / 62,784 bytes**, **418,941 / 42,540 bytes**, **728,151 / 25,384 bytes**였다.
- placeholder 키를 사용한 빌드 검증이며 Release·OTA·실기기 LED 관찰은 수행하지 않았다. 실기기에서는 역할별 Photo 색, Wi-Fi 차단 직후와 15초 경과 후 색 유지, Tagger Blink 단절 중 점멸 지속을 별도로 확인해야 한다.

## 2026-10-22 통신 복구 소프트웨어 검증

이 항목은 OTA 경로 통합을 포함했던 이전 구현의 검증 이력이다. 이후 사용자 요청으로 OTA 구조를 복원했으므로, 최종 상태는 아래의 **OTA 기존 구조 유지** 검증 항목을 따른다.

[통신 복구 변경](NETWORK_RECOVERY.md)의 최종 소스로 독립 검토와 로컬 검증을 완료했다. 현장 장애 원인은 미확정이며, 아래 결과는 실기 RF·OTA 성공이나 운영 배포를 의미하지 않는다. 기존 미커밋 변경을 보존했다.

- C++ 호스트 테스트 실행 파일 **19개 통과**.
- Python 도구/통합 회귀 테스트 **24개 통과**. 이 중 실제 수정 transport/parser를 컴파일하는 HTTP 장애 주입은 **31개 시나리오**를 검증했다.
- 무응답/slow drip/조기 EOF/chunk/trailer/크기 제한/429·503, 재접속 임계값과 millis 순환, 명령 취소/busy 해제, RTC 재시작 예산, 실제 OTA install 함수의 실패 시 abort를 확인했다.
- 독립 검토에서 확인한 SDK connect 오버로드 재귀, 마지막 flash write 시간 초과 후 commit 가능성, 503 오류 본문 정체의 Wi-Fi 장애 오인, SDK end 수신 drain 정체를 수정하고 재검증했다.
- ESP32 Arduino **3.3.11**, 공개 link-validation 키를 사용하는 배포 금지 빌드로 아래 **5개 설정**이 모두 컴파일·링크됐다. 일반 placeholder로 최적화되는 OTA 경로를 피하고, TTGO/TagMachine ELF에서 실제 `checkPinned` 링크를 확인했다.
- bounded HTTP 심볼은 TTGO에 존재하고 TagMachine Main에는 없다. 기능 선택용 함수 포인터로 공유 장치의 불필요한 코드 링크를 제거했다. TagMachine의 32KiB 슬롯 여유 기준도 통과했다.

## 2026-10-22 OTA 기존 구조 유지 — 최종

사용자 요청에 따라 앞선 OTA 통합을 철회했다. 최신 OTA는 원래 SecureOTA의 `version.txt/update.bin/update.sig`를 사용하고, 명시적 버전 지정은 기존 `checkPinned`를 사용한다. 최신 업데이트에 새 manifest/archive가 필요하지 않다. 공통 `IoTGloveOtaClient.cpp/.h`는 수정 전 git HEAD와 바이트 단위로 동일하게 복원했다. 새 OTA transport/progress hook과 해당 테스트는 제거했으며, 배포·서명 형식과 두 보드 업데이트 순서를 변경하지 않았다.

일반 HTTP 제한·Wi-Fi 복구·작업 감시는 유지한다. 진행 hook이 없는 기존 OTA 실행과 완료 콜백은 새 worker 정체 감시에서 제외하며, 반환 후 일반 감시를 재개한다. OTA 자체의 기존 정체 가능성을 새로 해결한 것은 아니다.

- 작성자와 다른 검토자가 OTA 분기·callback·감시 범위를 검토했다.
- C++ 호스트 테스트 **18개**, Python 회귀 테스트 **24개** 통과. 실제 bounded HTTP 장애 시나리오 **31개**도 재통과했다.
- 신규 `test_ota_compatibility.py`는 실제 생산 함수를 추출하여 기존 URL·최신/지정 버전 선택·성공/skip/실패·서버 명령 확인·OTA 중 감시 제외·반환 후 감시 복구·compile-only 차단을 검증한다.
- 공개 시험 키로 실제 OTA 경로를 포함한 **5종 빌드 모두 exit 0**. TTGO ELF에 `SecureOTA::check()`와 원래 `checkPinned`가 있고 제거한 OTA transport는 없음을 확인했다.
